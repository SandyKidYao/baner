# ADR-0004:加密使用 age 格式,两层钥匙

## 背景

加密 tab 的内容和 tab 名在仓库里必须是密文(D5)。用户只记一个主密钥。块文件有几百个,打开 tab 必须快(D1)。

## 选项

### 选项 A:age 格式,两层钥匙
- 做法:应用生成一把 age X25519 身份(文件钥匙)。所有加密文件都以它为接收者加密。身份本身用主密钥(age 口令模式,scrypt)加密后,存为 `.baner/identity.age`,随仓库同步。
- 优点:每台设备只在首次配置时做一次慢速的 scrypt 计算,之后解密每个文件都很快;用开源的 `age` / `rage` 命令行工具加上主密钥,就能脱离 Baner 取回所有数据;更换主密钥只需重新包裹身份文件,不用重新加密所有块。
- 缺点:每次加密生成的密文都不同(随机 nonce),所以只在明文变化时才重新加密。

### 选项 B:自定义格式(XChaCha20-Poly1305 + Argon2id)
- 优点:很快;格式完全由自己控制。
- 缺点:离开 Baner 就没有现成工具能解开;格式设计和审计要自己负责。

### 不采用:直接用口令加密每个文件
- 每个文件都要做一次 scrypt(约 1 秒),几百个块完全不可用。

## 决定

采用 A(用户 2026-11-10 确认)。

## 理由

用户放进加密 tab 的是密钥这类关键内容。「Baner 出问题时也能用标准工具取回」的价值,高于自定义格式带来的灵活性。两层结构同时解决了速度和更换主密钥的问题。

## 后果

- 正面:有标准的逃生通道;更换主密钥的成本很低。
- 负面与代价:
  - 主密钥一旦泄露,而攻击者又拿到了仓库,就能解开身份文件。这时必须同时轮换身份,并重新加密所有文件。MVP 不做这个功能,记为后续。
  - 文件名里的排序键和块 id 是明文,会暴露块的数量和大致大小,但不暴露内容和 tab 名。
- 什么情况下应该重新审视:需要多人共享加密 tab 时(age 天然支持多个接收者,届时扩展即可)。
